# Code, feature and build audit — 2026-10-13

Scope: `main` at `ac5d4ed`, plus `feat/read-only-graylog-lookup` / PR #1. Reviewed the repository tree (excluding vendored skills), JavaScript modules, browser UI, CLI, Node tests, GitHub workflow, README and v1.2 product specification. This is a source and automated-test audit, **not a certification against a running Graylog instance**.

## Product status

The current deliverable is a static, dependency-free browser JSON trace viewer with field deltas, provenance labels, diagnostics and export. PR #1 adds a Node CLI for permission-checked retrieval of a stored document by index and ID. There is **no Java plugin code, plugin manifest/JAR, native Graylog UI action, or original-execution collector**. All non-observed flow information still depends on supplied or synthetic trace files.

## Bugs and correctness concerns

| Priority | Finding | State / evidence |
| --- | --- | --- |
| P1 | Graylog API token auth instructions and CLI were wrong: access tokens are the Basic **username**, with literal `token` as password; documented `GRAYLOG_USER:GRAYLOG_TOKEN` would fail. | Fixed in PR #1; tests added; verified against official Graylog 7.1 REST access token documentation. |
| P2 | `fieldHistory` previously recalculated full deep diffs for **every field** on a single-field selection. Complexity and UI stalls could become significant with large traces. | Fixed in PR #1 by selecting only the requested field before diffing; regression tests added, including prototype-shaped names. |
| P2 | `validateTrace` did not bound nested evidence depth or reject cyclic programmatic input before cloning/diffing, which could trigger recursion or cloning failures. | Fixed in PR #1 with iterative depth/node checks, preserving legitimate JSON nulls; tests added. |
| P1 risk | The REST adapter's accepted JSON envelopes are covered by mock tests only, not verified against a live Graylog 7.1.3 response or its reverse-proxy configuration. | Open; staging integration test required before production reliance. |
| P1 risk | Stored final fields and streams are **not** a record of the original rule sequence, lookup responses, routing mutations, or timing. A reconstruction could be mistaken for history unless provenance stays prominent. | Current viewer separates provenance and explicitly avoids historic execution claims; preserve this contract during native integration. |
| P2 risk | The browser has no automated DOM, keyboard-navigation or accessibility regression suite. | Open. |
| P2 risk | Test/CI validation covers Node unit tests only. No Graylog server integration suite, browser smoke test, Java build, plugin packaging, load testing, static analysis, or authorization matrix. | Open. |
| P2 risk | Trace export can include sensitive original message contents and relies on the user to protect the exported file. No field-level redaction/authorization layer beyond what the upstream API returns exists. | Open; avoid claims of sanitized exports. |
| P2 risk | Native recording/simulation hooks have not been proved to be safe or available in Graylog 7.1.3. Using the normal interpreter for replay may cause side effects. | Do not enable replay/recording before isolated staging verification. |

No exposed credentials or known direct production configuration mutation paths were found in the small application code reviewed. This does not establish the absence of vulnerabilities or validate a future plugin implementation.

## Recommended delivery order

1. **Finish and merge the tested read-only CLI change.** Verify real token auth and the actual Graylog 7.1.3 response schema with a least-privilege staging account, plus 401/403/404 cases, before calling the integration complete.
2. **Build the minimal native plugin skeleton** pinned to server/web versions, with isolated build checks and a permission-aware `Trace Message` action. Keep production Graylog untouched until staging verification.
3. **Add topology resolvers** for input, processor order, pipelines, streams and index sets, each with explicit OBSERVED/RECONSTRUCTED/UNKNOWN evidence statuses and permission handling.
4. **Expand the UI**, starting with rule graph, storage and timeline from real resolver output, plus keyboard/accessibility testing.
5. **Prove a side-effect-free simulation adapter** using Graylog's supported interpreter APIs in an isolated test instance. Never run an ordinary live processor on a copied message.
6. **Research and test recording hooks**, then implement bounded capture, redaction, retention, sampling and cluster-safe expiry. Only then expose recording controls.
7. Add snapshot replay/comparisons, event relations, richer diagnostics, YAML export, load tests and packaging/compatibility checks.

## Acceptance gates before claiming an alpha plugin

- A reproducible native build produces an installable plugin for a pinned Graylog release.
- The message action successfully opens an authorized stored message in Graylog; other-account stream restrictions and deleted/unavailable objects behave correctly.
- No production message, stream, pipeline, rule, index or event configuration is mutated by default tracing.
- Unavailable execution evidence is always explicitly UNKNOWN rather than invented.
- CI verifies Node/Java tests, server integration, UI smoke tests and a minimal permission regression suite.

Until these gates pass, describe this repository as a **standalone development viewer plus experimental stored-message lookup**, not a functional Graylog Message Trace plugin.
